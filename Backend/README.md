# Smart Caspian Transit

Предиктивный цифровой двойник мультимодального хаба МТК «Север–Юг»: архитектура локального MVP для хакатона.

**Статус:** реализованы `ml_predictor.py`, `routing_engine.py`, `smart_customs.py`, `jit_optimizer.py`, объединяющий модуль `smart_customs_and_jit.py` и основной API в `Backend/main.py`. Модули внутри `app/` остаются каркасом целевой архитектуры.

## JIT Arrival и ESG

`POST /api/v1/optimize/jit` принимает `distance_nm` (морские мили, > 0), `current_speed_knots` (узлы, >= 6), `port_delay_hours` (часы, >= 0). Задержка — **дополнительное ожидание после исходного ETA**, а не время до освобождения причала от текущего момента.

Формула: `new_speed = max(6, distance / (distance / current_speed + port_delay))`. При нулевой задержке скорость не меняется. При ограничении в 6 узлов точное прибытие может быть невозможно; API возвращает остаточное ожидание. Нулевая дистанция, скорость ниже 6, отрицательная задержка и нечисловые/неограниченные значения отклоняются с 422.

Пример запроса:

```json
{"distance_nm": 120, "current_speed_knots": 12, "port_delay_hours": 5}
```

Результат (числа округлены для чтения):

```json
{
  "new_speed_knots": 8.0,
  "arrival_in_hours": 15.0,
  "berth_available_in_hours": 15.0,
  "remaining_wait_hours": 0.0,
  "baseline_fuel_tonnes": 1.728,
  "optimized_fuel_tonnes": 0.768,
  "fuel_saved_tonnes": 0.96,
  "co2_saved_tonnes": 2.98944,
  "fuel_coefficient": 0.0001
}
```

Часовой расход `k * speed^3` умножается на время перехода `distance / speed`. Итого топливо за переход: `k * distance * speed^2`; экономия CO₂ равна экономии топлива в тоннах, умноженной на 3.114. Для фиксированной дистанции нельзя использовать разницу кубов скоростей как экономию топлива за весь рейс.

**Калибровка демо:** `k = 0.0001 т/(ч·узел³)` — условное значение, а не данные реального судна. Функция `calculate_esg(..., fuel_coefficient=...)` позволяет передать калиброванный коэффициент; API пока использует демо-значение и возвращает его явно. Числа относятся ко всему судну, не к одному TEU из графа маршрутизации. Расход на якоре, вспомогательные двигатели, течение и волны в этом приближении не учитываются. Нижняя граница 6 узлов задана ТЗ, а не определяется оценкой реальных навигационных условий.

Для согласования видов транспорта внешняя система должна вычислить момент готовности причала, перегрузки, поездов/авто и таможни и преобразовать его в дополнительное ожидание относительно исходного ETA. Текущий JIT принимает одно готовое значение задержки; расписания и таможенные очереди он не прогнозирует. ML-модуль прогнозирует транспортные задержки по заданной погоде, а **прогнозирование самой погоды Каспийского моря пока не реализовано**: для него нужны временные ряды метеонаблюдений, координаты маршрута и горизонт прогноза.

```powershell
..\.venv\Scripts\python.exe -m pip install -r requirements.txt
..\.venv\Scripts\python.exe -m uvicorn main:app --reload
```

Swagger UI: `http://127.0.0.1:8000/docs`. Используйте один worker. При старте `lifespan` генерирует 1000 рейсов, обучает модель и создает граф; запросы используют готовые ресурсы. Синхронные обработчики выполняются в пуле потоков. CORS разрешает все origins без credentials.

`POST /api/v1/route/calculate` принимает `source`, `target`, `current_weather` (0–10) и необязательный `season` (по умолчанию `summer`). Возвращает самый быстрый маршрут: `nodes`, `total_time_hours`, `total_cost_usd`. Графовый движок сам вызывает предиктор для каждого ребра, поэтому задержки не прибавляются дважды. Экологичный вариант пока доступен через Python-функцию движка.

`POST /api/v1/customs/clear` принимает `cargo_payload` с полями `weight` (кг, больше 0), `type`, `id` (непустой строковый ID), а также `provided_hash` (64 hex-символа). Для совместимости также принимается прежняя форма запроса: `cargo_data` с полями `weight`, `type`, `sender`, `recipient`. Используйте одну из двух форм, без смешивания полей. Совпадение дает `{"status":"Pre-cleared","green_corridor":true}`, несовпадение — `{"status":"Requires inspection","green_corridor":false}`. Статусы возвращаются в ответе без хранения общего изменяемого состояния.

Правило хеширования: валидация четырех полей, вес как float, JSON с сортировкой ключей, без пробелов-разделителей, без ASCII-экранирования Unicode, UTF-8 и SHA-256. Пробелы и регистр внутри строк значимы. Для формирования совместимого хеша:

```python
from smart_customs_and_jit import calculate_customs_hash, optimize_vessel_speed

cargo = {"weight": 100, "type": "Зерно", "id": "C-001"}
digest = calculate_customs_hash(cargo)
payload = {"cargo_payload": cargo, "provided_hash": digest}
jit_result = optimize_vessel_speed(120, 12, 5)
```

API вызывает `verify_customs_hash()` и `optimize_vessel_speed()` из `smart_customs_and_jit.py`. JIT использует проверенные расчеты из `jit_optimizer.py`, сохраняя ограничение в 6 узлов, оценку остаточного ожидания и демонстрационный коэффициент расхода топлива. Возвращаются также исходный и оптимизированный расход (`baseline_fuel_tonnes`, `optimized_fuel_tonnes`). Прежние самостоятельные модули продолжают работать.

Это локальная имитация смарт-контракта: совпадение хеша проверяет согласованность данных, но не удостоверяет отправителя и не является реальным таможенным разрешением.

Ошибки API: 422 — некорректный запрос, 404 — неизвестный терминал, 409 — нет маршрута, 503 — модель не готова/ошибка прогнозирования, 500 — некорректная сеть. Пока используется стандартный формат FastAPI `detail`; единый формат ошибок из целевой архитектуры еще не реализован.

## Модуль 1: локальный запуск

### Новый морской пайплайн: ml_pipeline.py

`generate_mock_data(samples=5000, random_state=42)` возвращает DataFrame с колонками `departure_port`, `arrival_port`, `wind_speed_ms`, `wave_height_m`, `port_congestion_percent`, `season`, `delay_hours`. Выборки воспроизводимы; `samples` должен быть положительным целым числом.

Правила синтетической задержки складываются: база 0–4 ч; волна строго выше 2.5 м добавляет 12–24 ч; загрузка строго выше 85% добавляет 10–36 ч; зима при отправлении из Астрахани или Оли добавляет 24–48 ч. Добавляется гауссовский шум со стандартным отклонением 0.5 ч, итог ограничивается снизу нулем.

Категории: отправление — `Астрахань`, `Махачкала`, `Оля`; прибытие — `Энзели`, `Амирабад`; сезон — `Winter`, `Spring`, `Summer`, `Autumn` (регистр значим). Диапазоны числовых признаков: ветер 0–25 м/с, волны 0.1–4.5 м, загрузка 10–100%.

```python
from ml_pipeline import CaspianPredictor, generate_mock_data

df = generate_mock_data(samples=5000)
predictor = CaspianPredictor().train(df)
delay_hours = predictor.predict({
    "departure_port": "Оля",
    "arrival_port": "Энзели",
    "wind_speed_ms": 18.0,
    "wave_height_m": 3.2,
    "port_congestion_percent": 90.0,
    "season": "Winter",
})
```

В `__init__` создается Pipeline: `ColumnTransformer` с `OneHotEncoder` для категорий и `StandardScaler` для чисел, затем `RandomForestRegressor(n_estimators=100)`. `train(df)` обучает всю цепочку на переданных данных и возвращает экземпляр; `predict(features_dict)` возвращает `float` в часах. До обучения возникает `NotFittedError`. Отсутствующие поля, неизвестные категории, выход за диапазоны, NaN/Infinity и отрицательная целевая задержка отклоняются. При неудачном переобучении прежняя модель сохраняется.

Это сценарный генератор по заданным правилам, не калиброванный физический симулятор. Ветер и волны генерируются независимо; отдельный штраф за ветер не задан. Модель прогнозирует задержку по метеоданным, но не саму погоду. Для проверки качества используется отдельная синтетическая выборка и сравнение MAE с прогнозом среднего; это не оценка точности на реальных рейсах.

Новый `CaspianPredictor` имеет другой контракт признаков. Существующие API и графовый движок пока используют `TransitPredictor` из `ml_predictor.py`; новый модуль не подменяет его автоматически. Демонстрационный запуск из `Backend`: `..\.venv\Scripts\python.exe ml_pipeline.py`.

### Исходный предиктор: ml_predictor.py

Зависимости модуля перечислены в `requirements.txt`. Требуется Python 3.10+ с поддержкой используемых ML-библиотек; для локальной проверки используется Python 3.11.

```powershell
python -m venv ../.venv
..\.venv\Scripts\python.exe -m pip install -r requirements.txt
..\.venv\Scripts\python.exe ml_predictor.py
..\.venv\Scripts\python.exe -m unittest discover -s tests/unit -p "test_ml_predictor.py" -v
```

```python
from ml_predictor import TransitPredictor, generate_mock_data

data = generate_mock_data()  # 1000 записей, seed=42
predictor = TransitPredictor().train(data)
delay = predictor.predict_delay({
    "weather_severity": 7.0,  # 0–10
    "port_congestion": 80.0,  # 0–100 процентов
    "transport_mode": "ship",  # ship | rail
    "season": "winter",  # winter | spring | summer | autumn
})
print(f"Ожидаемая задержка: {delay:.2f} ч")
```

`TransitPredictor().train()` самостоятельно генерирует данные, если DataFrame не передан. Обучение выполняется явно один раз; импорт и `predict_delay()` не обучают модель. До обучения прогноз вызывает `ModelNotTrainedError`. Некорректные признаки вызывают `ValueError` / `pydantic.ValidationError`: проверяются диапазоны, категории, пропуски, NaN, бесконечности и лишние поля.

Датасет содержит четыре запрошенных признака, `delay_hours` и метаданные `origin` / `destination` (Астрахань, Махачкала, Энзели). Метаданные не участвуют в прогнозировании. Железнодорожные рейсы с Энзели условно обозначают сухопутные маршруты, а не наличие прямой железнодорожной связи. Формула синтетической задержки учитывает повышенную чувствительность судов к погоде, нелинейную перегрузку порта, сезон и случайный шум.

В текущем модуле используются только четыре запрошенных признака. Поскольку синтетические записи не содержат дат, тест качества использует случайную отложенную выборку 20% и сравнение MAE с постоянным прогнозом среднего. Временное разбиение, расширенный набор признаков и сохранение артефактов из целевой архитектуры относятся к последующим модулям. Модель хранится в памяти.

## Модуль 2: граф и маршрутизация

`create_transport_graph()` создает независимый ориентированный `MultiDiGraph` с четырьмя узлами: Астрахань, Махачкала, Энзели, Решт. Ребра содержат `base_time_hours`, `cost_usd`, `co2_emissions_kg`, а также `transport_mode` и `port_congestion` для ML. Обратные направления заданы явно; параллельные ребра сохраняют транспортные альтернативы.

```python
from ml_predictor import TransitPredictor
from routing_engine import find_optimal_route

predictor = TransitPredictor().train()
routes = find_optimal_route(
    "Махачкала", "Решт", predictor, current_weather=7.0, season="winter",
)
print(routes["fastest"]["nodes"], routes["fastest"]["total_time_hours"])
print(routes["eco"]["nodes"], routes["eco"]["total_co2_emissions_kg"])
```

`current_weather` — одно число 0–10 для всей сети на момент запроса. `season` по умолчанию равен `summer` как явное допущение демо; для другого сезона передайте его явно. Необязательный `graph=` позволяет использовать измененную сеть. Переданная сеть не изменяется; задержка каждого ребра вычисляется один раз на запрос. Затем два поиска Дейкстры минимизируют соответственно `base_time_hours + predict_delay(features)` и `co2_emissions_kg`. Для каждого критерия выбирается свое параллельное ребро с сохранением его идентификатора. При равных весах выбирается первый найденный вариант; два маршрута могут совпасть.

Результат — словарь `fastest` / `eco`. Каждый маршрут содержит `nodes`, `segments`, `total_base_time_hours`, `total_delay_hours`, `total_time_hours`, `total_cost_usd`, `total_co2_emissions_kg`. Сегменты включают идентификатор ребра, вид транспорта и отдельные показатели. CO₂ — единственный экологический критерий MVP, не полноценная оценка ESG.

Время, стоимость и выбросы демонстрационные; стоимость и выбросы относятся к перевозке одного TEU. Ребра обозначают укрупненные маршруты с возможными промежуточными участками и не подтверждают наличие прямых железнодорожных связей. В модуле 2 узлы — города/терминалы; отдельные состояния транспорта и ребра перегрузки из целевой архитектуры еще не реализованы. Веса фиксируются на момент запроса, изменение погоды по мере движения не моделируется.

Ошибки: `UnknownNodeError` — неизвестный терминал; `RouteNotFoundError` — нет направленного пути; `InvalidGraphError` — некорректные атрибуты ребра; `PredictionError` — ошибка модели или невалидная задержка (исходное исключение доступно через `__cause__`). Невалидная погода/сезон вызывает Pydantic `ValidationError`. Для одинаковых начальной и конечной точек возвращаются два нулевых маршрута без обращения к модели.

## Назначение MVP

- Представлять логистическую сеть портов, терминалов и транспортных связей.
- Строить маршруты по времени или стоимости с учетом вида транспорта и перегрузок.
- Предсказывать задержки на транспортных сегментах и рассчитывать ожидаемое время прибытия.
- Сравнивать базовый маршрут со сценарием закрытия сегмента, снижения пропускной способности или увеличения загрузки.

Погодные условия и загрузка задаются входными данными; внешние интеграции не требуются. Демонстрационные данные синтетические, результаты не являются подтвержденными эксплуатационными прогнозами.

## Архитектура

Модульный монолит: один процесс FastAPI, граф NetworkX в памяти, CSV на диске и локальный артефакт scikit-learn. Pandas используется для подготовки данных. Pydantic отвечает за проверку входных и выходных API-контрактов и конфигурации.

```text
HTTP → API / Pydantic → сервисы → репозиторий NetworkX
                           └──→ ML-предиктор → локальный артефакт

CSV → Pandas / признаки → обучение scikit-learn → артефакт
```

API проверяет запросы и преобразует ошибки в HTTP-ответы. Сервисы выполняют бизнес-операции без зависимости от FastAPI. Репозиторий управляет графом и его снимками. ML-модули отвечают за подготовку признаков, обучение и инференс; обучение не выполняется внутри HTTP-запросов. Доменные модели не зависят от API и инфраструктуры.

### Граф и маршрутизация

- Ориентированный `MultiDiGraph` поддерживает несколько транспортных сегментов между одной парой узлов.
- Вершина — состояние «терминал + вид транспорта». Перегрузка моделируется отдельным ребром внутри терминала, поэтому ее время и стоимость явно участвуют в поиске маршрута.
- Ребро содержит устойчивый идентификатор, вид транспорта или признак перегрузки, расстояние, базовое время, стоимость, пропускную способность, загрузку и доступность. Для количественных полей фиксируются единицы измерения: км, часы, TEU/сутки, доля загрузки и единая валюта сценария.
- Для поиска выбирается одна неотрицательная аддитивная метрика: ожидаемое время или стоимость. Поиск сохраняет идентификаторы конкретных ребер, включая параллельные связи. Недоступные ребра исключаются.
- Ожидаемое время складывается из базового времени и прогнозируемых задержек транспортных ребер, а также длительности перегрузок. ETA получается добавлением этого времени к моменту отправления с часовым поясом.
- Сценарий работает на отдельной глубокой копии графа. Базовая сеть не изменяется. Замена базовой сети валидируется целиком и выполняется атомарно с новой версией.
- MVP запускается с одним worker: несколько процессов получили бы независимые графы. Изменения в памяти теряются после перезапуска; исходные CSV позволяют восстановить демонстрационную сеть.

### ML-предиктор

Целевая переменная — задержка транспортного сегмента в часах. Признаки включают вид транспорта, расстояние, загрузку, пропускную способность, погоду и календарные признаки отправления. Допускаются только признаки, доступные на момент прогноза; фактическое время прибытия не используется как вход.

Общий `Pipeline` scikit-learn объединяет предобработку категориальных и числовых признаков с регрессором. Обучение и инференс используют одинаковый контракт признаков. Проверка качества выполняется на более позднем временном интервале; MAE сравнивается с простым baseline. Синтетические данные демонстрируют работоспособность, а не реальную точность.

Артефакт содержит модель, версию признаков, метаданные обучающей выборки и метрики. Загружаются только доверенные локальные артефакты. При отсутствии модели API явно сообщает о недоступности прогнозирования; базовая маршрутизация остается доступной. Отрицательные прогнозы задержек ограничиваются нулем с явным правилом в предикторе. Сумма точечных прогнозов не выдается за доверительный интервал.

### Контракты и ошибки

Все функции и публичные интерфейсы получат аннотации типов. Pydantic-контракты зададут диапазоны, единицы измерения, допустимые значения и запрет неизвестных полей. Ошибки будут возвращаться в едином формате: `code`, `message`, `details`, `request_id`.

Планируемые статусы: 422 — некорректные входные данные; 404 — неизвестный узел или сегмент; 409 — маршрут недоступен либо версия сети конфликтует; 503 — модель или сеть не готовы; 500 — внутренняя ошибка без раскрытия traceback клиенту. Логи содержат идентификатор запроса и версию графа/модели.

### Планируемые HTTP-контракты

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/health` | Состояние процесса, готовность сети и модели |
| `GET /api/v1/network` | Снимок сети и ее версия |
| `PUT /api/v1/network` | Валидация и полная замена базовой сети |
| `POST /api/v1/routes` | Маршрут по выбранному критерию с конкретными сегментами |
| `POST /api/v1/predictions` | Прогноз задержек заданных сегментов |
| `POST /api/v1/scenarios` | Сравнение базового и измененного сценария, включая отсутствие маршрута |

Это проектные контракты; маршруты пока не реализованы.

## Порядок последующей реализации

1. Зависимости, конфигурация, доменные модели, API-схемы и ошибки.
2. Демонстрационные данные, репозиторий графа и базовая маршрутизация.
3. ML-признаки, обучение, артефакты и прогнозирование.
4. Сценарии и сравнение маршрутов.
5. FastAPI, интеграционные проверки и инструкция локального запуска.

Реализация каждого блока начинается по отдельной команде пользователя. База данных, брокер сообщений, блокчейн, внешние погодные API, UI, авторизация и промышленная оптимизация потоков не входят в этот MVP.
