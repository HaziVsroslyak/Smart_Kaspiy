# Контракты и проверка интеграции

Из `Backend` запустите `..\.venv\Scripts\python.exe -m uvicorn main:app --reload`.
Swagger: http://127.0.0.1:8000/docs. Спецификация: `contracts/openapi.json`.
Перегенерация контрактов: `..\.venv\Scripts\python.exe -m scripts.export_contracts`.

## Фронтенд

Все POST принимают JSON. Ответы ошибок FastAPI содержат `detail` (строка или массив ошибок валидации).

| Путь | Запрос / назначение |
|---|---|
| GET `/api/v1/health` | Готовность моделей и наличие настройки погоды (не проверка валидности ключа) |
| POST `/api/v1/route/calculate` | `{"source":"Махачкала","target":"Решт","current_weather":7,"season":"winter"}` |
| POST `/api/v1/customs/clear` | `{"cargo_payload":{"weight":100,"type":"Зерно","id":"C-001"},"provided_hash":"64 hex символа"}` |
| POST `/api/v1/optimize/jit` | `{"distance_nm":120,"current_speed_knots":12,"port_delay_hours":5}` |
| POST `/api/v1/predictions/delay` | Шесть признаков CaspianFeatures, описанных ниже |
| GET `/api/v1/weather/forecast?latitude=42&longitude=50` | Точечный прогноз; координаты примера не представляют весь маршрут |
| POST `/api/v1/predictions/delay-from-weather` | Координаты, `forecast_at` RFC3339 с часовым поясом, порты, `wave_height_m`, `wave_source`, `port_congestion_percent` |

Для последнего запроса сначала получите forecast, выберите `valid_at` из ответа. Ветер берется из ближайшего слота в пределах 90 минут, сезон — по месяцу UTC. Запрос за пределами доступного интервала возвращает 422. Высоту волн и загрузку порта предоставляет вызывающая сторона. Ветер выше 25 м/с отклоняется как выход за диапазон обучающей модели; значения не обрезаются.

Клиент `FrontEnd/src/api/client.ts` содержит три типизированные Axios-функции. `_meta` добавляется только клиентом: `mode=live` либо `mode=mock`. Сетевые ошибки, тайм-ауты и 5xx дают фиксированные демонстрационные ответы. Ошибки 4xx остаются ошибками. Mock таможни никогда не разрешает зеленый коридор. UI отображает предупреждение.

## Дата-инженер

`contracts/training_record.json` — схема строки для обучения. `contracts/caspian_features.json` — схема для предсказания. `contracts/training_sample.csv` — 10 **синтетических** записей UTF-8 без индекса.

| Поле | Формат |
|---|---|
| departure_port | Астрахань / Махачкала / Оля |
| arrival_port | Энзели / Амирабад |
| wind_speed_ms | число 0–25 м/с |
| wave_height_m | число 0.1–4.5 м |
| port_congestion_percent | число 10–100% |
| season | Winter / Spring / Summer / Autumn |
| delay_hours | неотрицательное число часов, только целевая переменная обучения |

В модели маршрутизации `TransitPredictor` иной контракт: weather_severity 0–10, port_congestion 0–100, ship/rail, сезон в нижнем регистре. Не подменяйте эти признаки физическими величинами автоматически. CaspianPredictor доступен отдельными эндпоинтами задержек. Обе модели пока обучаются на синтетике при запуске.

Для реального датасета храните отдельно trip_id, время отправления/планового и фактического прибытия, forecast_issued_at/valid_at, координаты и источники признаков. Цель определяйте как max(0, actual_arrival - planned_arrival) в часах; признаки доступны на момент прогноза. Разделяйте train/test по времени и рейсам, не используйте будущие наблюдения вместо исторически доступного прогноза. Эти метаданные пока не обязательны для синтетического train(df).

## OpenWeather

Перед запуском сервера задайте `OPENWEATHER_API_KEY` в окружении. Ключ не нужен React и не включается в Git. Скопируйте `.env.example` в `Backend/.env`: файл загружается при старте; переменная окружения имеет приоритет. После изменения ключа перезапустите backend. Docker Compose передает переменную из окружения.

Используется https://api.openweathermap.org/data/2.5/forecast с `units=metric`. Документация: https://openweathermap.org/api/forecast5 . Прогноз провайдера — до 5 суток, шаг 3 часа. Это внешняя метеомодель, а не собственный обученный прогноз погоды. В ответе есть UTC `valid_at`, `retrieved_at`, источник, единицы в названиях полей и признак кэша. Кэш 10 минут, максимум 128 точек. Устаревшие слоты не выдаются.

Высоты волн в этом продукте нет: `wave_height_m=null`, `wave_height_available=false`. Для физического морского прогноза требуется отдельный источник волн с проверенным покрытием Каспия. Данные одной точки не описывают погоду всего моря; для маршрута запрашивайте его контрольные координаты и соответствующее время.

503 — отсутствует/отклонен ключ или исчерпана квота; 504 — тайм-аут/сеть; 502 — некорректный ответ провайдера. Секреты и URL с ключом не возвращаются клиенту. Без ключа остальной backend работает. Живой запрос проверяется только после настройки действующего ключа.

## Проверка

### Маршрут на карте и погодный пересчёт

`POST /api/v1/route/calculate` сохраняет поля `source`, `target`, `current_weather` (теперь необязательное, по умолчанию 0) и `season`. Добавлено поле `weather` с двумя вариантами:

```json
{"source":"Махачкала","target":"Решт","season":"autumn","weather":{"source":"scenario","wind_speed_ms":22,"wind_gust_ms":27,"wave_height_m":3.2}}
```

```json
{"source":"Махачкала","target":"Решт","season":"autumn","weather":{"source":"openweather","latitude":42,"longitude":50,"forecast_at":"2026-11-12T18:00:00Z"}}
```

Во втором примере замените `forecast_at` точным `valid_at` из актуального `/api/v1/weather/forecast`. Сервер сам получает ветер/порывы; присылать значения ветра с `source=openweather` нельзя (422). Если слот уже недоступен, ответ 422 требует выбрать новое время. Ошибки провайдера возвращаются как 502/503/504. Никакие отсутствующие волны не подменяются нулями: в ответе сохраняется null. Переданный `season` применяется к ML-модели; интерфейс выбирает сезон по времени прогноза, допускает ручное изменение.

Ответ содержит прежние `nodes`, `total_time_hours`, `total_cost_usd` и новые поля:

- `segments`: источник, назначение, `edge_id`, `transport_mode` (ship/rail), базовое время, задержка, итоговое время, стоимость и CO₂ каждого участка.
- `total_base_time_hours`, `total_delay_hours`, `total_co2_emissions_kg`.
- `eco`: маршрут с минимальным CO₂ в том же формате, без вложенных eco/weather.
- `weather`: использованные величины, источник, координаты, время прогноза/получения, severity, sea_restricted, reasons, scope и policy.

Правило `demo-v1`: ветер или порывы ≥ 20 м/с либо волны > 2,5 м исключают все морские рёбра из копии графа. Это **демонстрационная политика**, не официальное ограничение судоходства. Для текущего TransitPredictor применяется явный эвристический адаптер `severity=min(10,max(max(wind,gust)/25*10,wave/4.5*10))`; отсутствующая величина не участвует. Полученная интенсивность влияет на задержки всех участков текущей упрощённой модели. Правила и шкалу необходимо калибровать по историческим данным и характеристикам судов. CaspianPredictor в эту ветку не подставляется: у него иной контракт.

Расчёт использует один выбранный прогноз как репрезентативный для всего пути. Пространственно-временная погода по каждому морскому участку пока не реализована. Если после ограничений пути нет — 409. При улучшении условий исходные морские связи снова доступны: общий граф не изменяется.

Frontend сохраняет параметры маршрута при переходе в «Погоду». Кнопка «Применить к маршруту» передаёт выбранный слот и запускает пересчёт. При подключённом прогнозе повторный запрос выполняется каждые 60 секунд; серверный погодный кэш остаётся 10 минут. Изменения условий вручную пересчитываются через 400 мс; устаревшие ответы отменяются/игнорируются. Неизменные ответы опроса не заменяют сохранённое сравнение. При ошибке погодного расчёта карта очищается, показывается ошибка, фиксированный mock не выдаётся за новый путь.

Карта Leaflet/OSM показывает **схему связей**. Морские участки идут по промежуточным точкам в акватории и проверяются тестами на пересечение береговой линии Natural Earth 1:10m; это не точные фарватеры. Точки морских подходов отделены от городских меток; речной подход через дельту к Астрахани не показан. Ж/д линии остаются схемой связей. Синий — море, оранжевый пунктир — ж/д, серый — предыдущий результат. Координаты терминалов приблизительные. В графе есть автомобильные участки road; подробности ниже. Метрики CO₂/стоимость даны на 1 TEU и демонстрационные.

Демо: «Маршрут» → «Спокойно» → «Усиление ветра» → «Шторм · сценарий» → «Спокойно». Проверить изменение времени, транспорта, карты и восстановление морского пути. Затем «Погода» → порт/точка → время → «Применить к маршруту». Дополнительный API-ключ для карты не нужен; загрузка OSM-подложки требует сети.

Из `Backend`: `..\.venv\Scripts\python.exe -m unittest discover -s tests/unit -v` и `..\.venv\Scripts\python.exe -m unittest discover -s tests/integration -v`.
Погодные тесты используют фикстуры провайдера; это не проверка реального аккаунта OpenWeather.
Из `FrontEnd`: `pnpm install`, `pnpm test`, `pnpm build`, `pnpm dev`.


## Автомобильный транспорт

`transport_modes` в запросе маршрута: непустой массив из `ship`, `rail`, `road`.
По умолчанию разрешены все три. Пример только для авто:

```json
{"source":"Махачкала","target":"Энзели","transport_modes":["road"],"road_conditions":{"congestion_percent":20,"condition_severity":2,"border_wait_hours":4,"closed":false}}
```

Авторёбра: Астрахань–Махачкала (12 базовых часов, $550, 160 кг CO₂),
Махачкала–Энзели (32 ч, $800, 250 кг), Энзели–Решт (1 ч, $80, 15 кг).
Обратные связи присутствуют. Цифры демонстрационные, на 1 TEU.
Сохранённая автомобильная геометрия международного участка проходит через
Грузию и Азербайджан, поэтому учитываются три границы. Короткий коридор через
Самур в этом варианте не моделируется. Допуски грузов/перевозчиков и открытие КПП
не проверяются внешним API. Режим closed исключает все автомобильные рёбра
только из копии графа конкретного запроса. Невозможный маршрут возвращает 409.

`road_conditions`: congestion_percent 0–100 (default 20), condition_severity
0–10 (default 0), border_wait_hours 0–168 **на одну границу** (default 4),
closed bool (default false). Участок Махачкала–Энзели получает 3 * border_wait_hours;
внутренние участки — 0. Поле `border_wait_hours` в ответе каждого сегмента —
уже суммарное ожидание и является частью delay_hours, а не добавкой к total_time_hours.
В response также возвращаются применённые road_conditions и transport_modes.

TransitPredictor обучается на ship/rail/road и двух новых числовых признаках:
road_congestion_percent (0–100), road_condition_severity (0–10). Для старых
предсказаний и старых датасетов эти поля имеют default 0. Синтетический road-таргет
содержит погодную составляющую, 0.12 * congestion и 1.5 * condition. Ожидание на
границе добавляется детерминированно в графе после ML-прогноза, чтобы не учитывать
его дважды. CaspianPredictor морских задержек остаётся отдельной моделью.

Фронтенд позволяет выбирать разрешённые виды транспорта, менять дорожные
условия/очереди и закрывать автодороги сценарием. Изменения запускают тот же
пересчёт и сравнение маршрутов. Авто выделено фиолетовым; геометрия сохранена
локально из OSRM/OpenStreetMap, дополнительный ключ для неё не нужен.
Это геометрия driving, без проверки ограничений грузовика; для обратной схемы
переиспользуется обратная линия. Время/стоимость/выбросы берутся из графа.
Диспетчерские расписания и полноценная синхронизация перегрузки судно–поезд–авто
остаются отдельной задачей: этот расчёт выбирает цепочку транспорта и оценивает задержки.


## Прогноз перевозки по контрольным точкам и неизменяемый план

Основная вкладка «Маршрут» теперь использует отдельный сценарий рейса. Старый
`/api/v1/route/calculate` сохранён для совместимости со своим прежним контрактом.

- `POST /api/v1/voyages` — рассчитать и сохранить исходный план (201).
- `GET /api/v1/voyages/{id}` — загрузить исходный план и последний прогноз.
- `POST /api/v1/voyages/{id}/reforecast` — обновить прогноз без изменения плана.

Пример создания:

```json
{
  "source": "Махачкала",
  "target": "Решт",
  "departure_at": "2026-11-12T18:00:00Z",
  "transport_modes": ["ship", "rail", "road"],
  "connections": [{
    "terminal": "Энзели",
    "transport_mode": "rail",
    "first_departure_at": "2026-11-14T12:00:00Z",
    "interval_hours": 12,
    "handling_hours": 2
  }],
  "conditions": {
    "weather_mode": "openweather",
    "port_congestion": {"Энзели": 45},
    "road": {"congestion_percent": 20, "condition_severity": 0, "border_wait_hours": 4, "closed": false}
  }
}
```

Замените даты актуальными. Временные метки обязательно содержат часовой пояс.
Для сценария вместо openweather задайте weather_mode=scenario и объект
`scenario={"source":"scenario","wind_speed_ms":22,"wind_gust_ms":27,"wave_height_m":3.2}`.
Условия пересчёта передаются в том же объекте `conditions`; `{}` повторно использует
последние условия. Маршрут, отправление и расписания исходного плана не заменяются.

Ответ VoyageResponse содержит id, request, conditions, baseline, current,
eta_change_hours, route_changed, revision. baseline/current — снимки с fastest,
eco, calculated_at, excluded_reasons, alternative_reasons и training_data=synthetic.
В каждом маршруте есть departure_at, eta, coverage=complete/partial, reasons,
узлы, участки и прежние суммы времени/стоимости/CO₂. Участок дополнительно содержит
checkpoints, departure_at, arrival_at, connection_wait_hours, features_used,
eta_converged и reasons. Итоговое время участка включает ожидание стыковки;
`departure_at` участка — фактическое отправление после этого ожидания.

Контрольная точка содержит координаты, passage_at, forecast_at, retrieved_at,
wind_speed_ms, wind_gust_ms, wave_height_m, severity и status. В реальном режиме
берётся ближайший трёхчасовой слот в пределах 90 минут от времени прохождения.
Если подходящего слота нет — status=outside_horizon, величины null, покрытие
маршрута partial. Неизвестная погода не экстраполируется; модельная оценка на
непокрытой части не содержит подтверждённого погодного фактора. Такой ETA следует
рассматривать как неполный, а не как прогноз штиля. Сетевые ошибки провайдера
завершают обновление ошибкой, сохраняя предыдущий успешный прогноз.

Морские точки: подход отправления, центральный Каспий, подход прибытия.
На международном автоучастке дополнительно Тбилиси и Баку; для прочих наземных
связей — терминалы. Прогресс по времени приблизительный (0/0.5/1 для моря,
0/0.35/0.72/1 для авто в прямом направлении). Точки не заменяют полноценную
геометрическую/скоростную модель движения. Каждая уникальная локация запрашивается
один раз за расчёт, до четырёх запросов одновременно, затем действует общий кэш
OpenWeather 10 минут. Клиент ждёт до 90 секунд; актуальный рейс с openweather
пересчитывается раз в минуту, пока открыт интерфейс. Фонового серверного планировщика нет.

Время прохождения и ML-задержка уточняются до стабильного решения (до 6 итераций).
Временной сдвиг на предыдущем участке влияет на прогноз и стыковку следующего.
Граф малый, поэтому сервис сравнивает все простые пути до трёх рёбер; это учитывает
зависящие от времени ограничения и расписания, которые нельзя корректно свести
к прежнему статическому весу Дейкстры. Нестабильные варианты не выбираются и получают
объяснение; циклы и ожидание окончания шторма не оптимизируются.

Шторм проверяется только для морского участка в его точках и на его время:
ветер/порывы >=20 м/с либо сценарные волны >2.5 м. Причина исключения содержит
точку и время. Это правило MVP, не официальное закрытие порта. Для ML используется
максимальная интенсивность погоды по точкам участка, сезон по UTC-отправлению,
режим транспорта, загруженность терминала назначения и дорожные признаки.
TransitPredictor обучен на синтетике; физические величины и использованные признаки
возвращаются для проверки. OpenWeather здесь не даёт высоту волн.

Расписание периодическое: ready=прибытие+handling_hours; если ready позже первого
отправления, берётся первое доступное отправление через целое число interval_hours.
Ровно к отправлению — успевает. Без заданного расписания пропуск стыковки не
выдумывается. Ожидание включается в delay_hours и total_time_hours один раз.
Причины: weather, port_congestion (>85%), missed_connection, connection_wait,
border, storm_restriction, forecast_gap. Погодный/портовый вклад в часах — отдельные
контрфактические оценки модели, они не аддитивны. Проблемы медленных альтернатив
также возвращаются, чтобы объяснить смену маршрута в обход перегруженного терминала.

Хранилище: `Backend/artifacts/voyages.sqlite3`, SQLite из стандартной библиотеки.
Исходные request/baseline никогда не перезаписываются. current/conditions обновляются
атомарно с проверкой revision; конкурентное устаревшее обновление получает 409.
Ошибка погоды/расчёта не меняет сохранённые данные. Перезапуск backend сохраняет планы.
Frontend хранит только активный id в localStorage, восстанавливает данные с сервера
и сравнивает с исходным baseline, а не с предыдущим опросом. «Новый исходный план»
начинает новый рейс, старые записи сохраняются. Для Docker необходимо монтировать
